# 匿名多版本评估规范

## 目的

比较同一交易日、同一输入条件下多份复盘的决策质量。支持A/B或A/B/C；评估器在评分锁定前不知道每份报告对应哪个Skill，也不得从文件名或格式猜测身份。

正式三版本测试必须为每个版本保留两类原始产物：

1. **最终实跑报告**：模型最终交付的完整Markdown；
2. **过程JSONL**：由外部测试runner原样捕获工具调用、检索、数据读取、错误与重试等过程事件。Skill本身不得为了评测伪造“思考过程”或补写JSONL。

三版本必须使用同一任务、同一目标交易日、同一用户输入、等价数据权限和隔离的存档/临时目录。不得让后跑版本读取前一版本生成的复盘。

## 第一阶段：T日盲评报告

隐藏T+1结果，分别评价：

- 机会召回（重点检查是否漏掉已具备多核心、独立逻辑与容量确认的高显著方向）；
- 风险召回；
- 主线/生命周期判断；
- 核心股识别与同行覆盖；
- 因果归因（Driver/Confirmation/事实/推断）；
- 数据纪律（日期、口径、缺失、冲突、降级）；
- 噪声控制与信息密度：重点检查②③④是否重复同一事实、Driver和股票故事；
- 次日可执行性与仓位边界。

每项1～5分并给一句可核对理由。先独立评分，再比较总体偏好；不得因篇幅更长、股票更多或措辞更确定而加分。

## 第二阶段：过程JSONL审计

在不评价隐藏链式思维的前提下，只审计可观察的执行行为：

- 是否完成关键扫描覆盖，是否过早从“发现”切到“组织答案”；
- 是否出现无效重复检索、同一证据反复搜索或明显资源浪费；
- 关键结论前是否实际取得对应证据；
- 数据源失败后是否正确降级/重试，而不是静默跳过；
- 用户偏好是否在全市场发现之前污染搜索范围；
- 候选压缩前是否完成六视角Discovery矩阵；数据允许时去重后是否达到8～12个独立候选/异常（优先约10个），少于8个时是否有“六视角已完成 + 市场稀疏/数据缺失”的可核对理由；
- 第一轮Discovery query是否保持中性，是否在本轮证据尚未发现某板块/股票前就用已知答案做命名搜索；
- 候选是否来自多个独立视角，还是用同一涨幅榜/同一产业链概念别名凑数量；容量型、逆势相对强弱型、事件型和风险型候选是否有被覆盖；
- 正式D编号冻结前是否完成跨候选合并终审；Discovery中可分开的上下游/相邻概念，若共享主要Driver、核心股高度重叠且次日验证条件基本相同，是否被重新合并而非重复占用D名额；
- 深研是否由明确的未解决决策问题触发，而不是对所有候选平均用力；是否存在结论已稳定后仍反复搜索同一事实；
- 正式D/R与`core_pool/watch_pool`冻结前是否完成截止时间内的最终重大反证扫尾；扫尾是否只覆盖正式对象而没有退化成第二次全市场Discovery；
- 命中重大反证后是否只重开受影响链路，并实际更新方向/核心/池子/仓位，而不是把反证孤立写在“风险提示”；若反证改变决策，JSONL是否存在带来源的`material_news_hit → decision_reopened → decision_change`完整证据链；
- Validator失败后是否针对错误修复，而不是绕过校验；
- 最终报告是否存在JSONL中没有证据来源的“突然结论”；
- 候选数量或D数量是否污染仓位：发现更多候选但市场风险预算、主线/核心质量和真正可执行机会未改善时，不得仅因“机会更多”提高仓位；
- 技术历史缺失是否只限制执行，而没有反向否定已经由基本面/方向/同行比较确认的核心身份；若技术数据缺失的条件核心仍在`core_pool`，是否明确冻结新增执行。
- Core Identity与Execution Permission是否严格分离：低仓、当前不可执行、无买点或技术missing不得被用作`core_pool=0`的决定性身份失败理由；若`core_pool=0`且存在正式D，是否有逐D `core_zero_audit`证明身份本身未通过。

Efficiency Pass附加检查：深研是否存在`unresolved_question/decision_field/expected_flip`；是否优先复用广扫证据；同链最终扫尾是否合理批量化而非逐股机械重复；多core共享相同技术缺口时是否使用全局技术门减少重复，同时没有隐藏个股差异；用户报告完整来源索引是否把全量审计信息留在JSONL而非正文。

v2.4.5附加检查：除v2.4.4全部纪律外，必须审计`environment_budget_audit`。弱市/防御/严重负宽度并叠加至少两个独立弱化族时，预算高于低仓必须有高门槛override；强市/正宽度/高接力且流动性或容量支持时，预算低于中高仓也必须有反向override；中性结构市不得因单一宽度/成交信号被机械压低，需保留指数与趋势容量的抵消作用。环境预算证据不得使用候选/D/core/watch数量。不得把“仓位更低”本身当成质量提升。


V2.4.6附加检查：不能仅凭`discovery_coverage_summary=6/6`或候选数8～12判Discovery完成。必须逐项审计六条`discovery_lens_scan`；容量Lens要检查高成交核心内部的重要分歧，Driver Lens要检查价格/政策/订单/业绩的独立信号，风险Lens要检查高位/高beta/容量负反馈。若Lens=`partial`且仍有高显著未决信号，只允许该Lens最多1次中性`coverage_repair_query`，并计入<=28总预算。用户报告同时执行Fact Ownership：同一完整事实只能由一个章节拥有，其余章节只写链路ID和增量动作；标准完整报告目标<=8500 chars，>8700必须接受output budget exception审查。

过程效率只作次级指标：更少调用不自动更好，更深搜索也不自动更好；以“完成必要覆盖的最小有效成本”为准。比较时同时看有效候选覆盖、会改变决策的证据数量、重复检索率和正式报告信息密度；不能用单纯搜索次数排名。

## 第三阶段：揭晓T+1

只评价：

- 情景覆盖是否合理，真实路径是否落在预案可解释范围；
- 推翻/降级条件是否及时；
- 交易计划能否按T日信息执行；
- 是否发生方向、个股、持仓、技术或仓位动作自相矛盾。

不得用“第二天涨了=昨晚正确”或“第二天跌了=昨晚错误”评价决策质量。

## 正式验收门槛

`a-stock-trading-review`只有在多日样本中同时满足下列条件，才可判定为通过正式验收：

- 机会召回不低于对照版本；
- 风险召回不低于对照版本；
- 主线/生命周期明显误判不增加；
- 数据日期与缺失纪律不退化；
- 次日计划可执行性不退化；
- JSONL未显示更严重的扫描遗漏、答案导向型首轮查询、偏好污染、方向过度拆分、候选数量灌水、平均用力式深研或无效资源消耗；
- Discovery召回在多日样本中不低于GitHub/v2.1等高召回对照，同时Discovery阶段调用成本不得因追求8～12候选而明显失控；
- 正式对象的重大反证漏报不得高于对照版本；最终扫尾不得演化成重复全市场扫描；
- 用户可见报告不得因内部研究加深而明显膨胀，除非新增内容直接改变决策；Efficiency Pass在同证据MVP中目标报告<=9000字符、第⑦步<=1400字符；v2.4.5正常完整日query-bearing事件目标<=28，超过时必须有逐项`research_budget_exception`证明存在可能翻转决策的问题；这些是效率目标而非凌驾于召回/风险纪律之上的硬KPI；
- 至少在两个重要维度上稳定优于对照版本，而不是只在单日总分领先。
- 版本升级遵循`release-gate.md`：Top3 D / Top2 R / core / candidate semantic stability、position consistency等关键维度不得低于v2.4.2冻结baseline；若尚未完成新版本多样本测试，只能标记Release Candidate，不得宣布Freeze。

若优势只来自单个交易日、措辞风格或偶然T+1结果，不判定更优。

## 输出

保留每个版本：T日报评分、JSONL过程审计、T+1评分、证据引用、最大优点、最大缺陷、总偏好。所有评分锁定后再揭晓版本身份，并给出“方法论问题 / 实现问题 / 数据问题 / 偶然结果”的归因。
